# 设计原则

> 内核定义 ArkSharp 的定位；设计原则用于指导功能设计、实现、测试和代码审查。

## 一、内核

ArkSharp 是面向 Unity/.NET 游戏开发，追求“轻快、顺手”的 C# 工具箱。

每项功能独立、按需取用；API 简单易用、符合惯例，兼顾热点性能，对开发者和 AI 都友好。

## 二、设计原则

### 1. 结构轻量：独立、分层、非侵入

- **独立按需**：每项功能可以独立、按需使用，只公开解决问题所需的最小能力。
- **避免框架化**：不要求项目采用统一基类、中央容器或强制生命周期，也不为潜在需求预先建立完整框架、扩展体系或多余包装。
- **按需分层**：复杂功能可以分层，每层只增加一个必要概念；上层组合下层，同时保留下层独立使用的能力，使用者可以停在适合自己的层级。
- **非侵入式组合**：优先通过泛型、委托、小型接口和对象组合连接功能，不要求业务类型继承 ArkSharp 基类。只有使用者主动进入的专业协议，才要求实现必要接口；继承只用于明确的类型关系，不作为连接业务代码的默认方式。

### 2. API 顺手：简单、惯用、贴合场景

- **简单易用**：正常路径保持简短，减少必须掌握的概念、配置和样板代码。
- **API 能够自解释**：通过直接的命名、清晰的类型和符合领域惯例的语义表达用法、前提和边界，避免依赖隐式约定和上下文猜测；对开发者容易理解和使用，也便于 AI 正确识别和调用。
- **按场景定义失败语义**：是否抛出异常、返回无效值或直接无操作，由使用场景和领域惯例决定；预期内的失败应便于调用者自然处理。
- **区分预期失败和前提错误**：调用者违反基本前提时，通常不做普遍兜底；只有语义明确且符合使用预期时，才提供安全调用或默认回退，且不能让编程错误无声消失。
- **非常规能力显式表达**：非惯用行为以及危险或专业能力，优先通过名称、类型和接口明确其使用前提、限制和失效条件，并适当补充简短说明和示例。

### 3. 实现克制：复杂度必须有明确收益

- **朴素实现**：默认选择直接、正确、符合语言与平台惯例的实现。
- **复杂度内聚**：内部复杂度必须换来更简单、一致的外部使用方式，不把基础设施配置和内部生命周期转嫁给调用者。实现可以较重，但普通 API 仍应保持轻量。
- **只优化明确热点**：只有明确的运行时热点，才引入额外的性能复杂度；性能优化应尽量封装在专用模块或底层，不泄漏到普通 API。
- **跨环境保持一致**：能够在 Unity/.NET 间复用的功能，应尽量保持一致的 API 和语义；环境特有的复杂度封装在内部，由环境差异造成的行为变化应明确表达。

### 4. 演进可信：意图清晰，行为可验证

- **必要的注释**：当代码结构和命名不足以说明非常规意图、边界处理或易错判断时，应补充注释，便于开发者和 AI 理解其目的、约束和使用场景。
- **可测试且独立**：涉及全局状态、环境分支或隐藏生命周期的功能，应提供可隔离的测试接缝；测试应可重复，不依赖执行顺序和偶然实现。
- **验证核心契约**：测试优先覆盖高风险边界、核心行为以及异常后的状态；基础逻辑与引擎行为分别在适合的环境中验证。
- **变更可审查**：每次开发变更都应让真实意图清晰、可验证、可审查。
