# DEV-GUIDE

这是一份通用工程开发手册，按需与项目特定指令合并使用。

**取舍原则：** 以审慎优先于速度。对于琐碎任务可自行判断。

## 1. 语言与编码

- 所有对话、说明、计划、总结、提交说明和项目文档默认使用简体中文输出（提交说明按项目约定调整）。
- 代码标识符、命令、文件路径、第三方 API 名称和必要的原文错误信息保留英文。
- 代码注释语言跟随项目已有风格；新项目默认简体中文。
- 所有文件使用 UTF-8 编码；通过 PowerShell 或其他脚本写入文件时，必须显式指定 UTF-8 编码，避免出现中文乱码。

## 2. 先思考再动手

**不要假设。不要隐藏疑惑。暴露权衡取舍。**

开始实现之前：

- 明确陈述你的假设。不确定就提问。
- 存在多种解读时列出选项——不要默默选一个。
- 存在更简单的方案时，主动提出。必要时提出反对意见。
- 有任何不清楚的地方，停下来，指出困惑所在，然后提问。

## 3. 简单优先

**用最少的代码解决问题。不做投机性开发。**

- 不做超出需求的功能。
- 单次使用的代码不做抽象。
- 不加未被要求的"灵活性"或"可配置性"。
- 不为不可能的场景编写错误处理。
- 如果你写了 200 行而 50 行就能搞定，重写。

判断标准：一位资深工程师是否会说"这过于复杂了"？如果是，简化。

## 4. 精准修改

**只改必须改的。只清理自己制造的问题。**

修改现有代码时：

- 不要顺手"改进"相邻的代码、注释或格式。
- 不要重构没有问题的代码。
- 匹配已有风格，即使你会用不同方式写。
- 发现不相关的废弃代码，提一句——不要删除。

当你的修改导致代码变为无用：

- 移除因你的修改而变得多余的 import / 变量 / 函数。
- 不要移除修改前就已存在的废弃代码，除非被要求。

检验标准：每一行改动都应能直接追溯到用户的需求。

## 5. 目标驱动执行

**定义成功标准。循环验证直到满足。**

将任务转化为可验证的目标：

- "添加验证" → "为无效输入编写测试，然后使其通过"
- "修复 bug" → "编写复现 bug 的测试，然后使其通过"
- "重构 X" → "确保重构前后测试均通过"

多步骤任务应在回复中先列出步骤和对应的验证项（无需落盘），再开始执行。成功标准越明确，越能独立推进。

## 6. 计划与执行

### 正式计划

- 预计修改 3 个以上文件、涉及跨模块联动或架构变更的开发任务，在开始修改生产代码前必须先输出正式 plan，并保存到 `docs/plans/`（按项目约定调整路径）。
- 除非用户明确要求直接执行，否则应等待用户确认 plan 后再实施。
- 任务中途发现方向变化时，应先更新 plan 再继续。

### 并行执行

- 开始实现前，先评估任务是否可拆分为多个独立子任务。可拆分时**必须使用子代理（sub-agents）**并行执行，不要用单代理串行完成可并行的工作。
- 子代理优先选用次一级模型（如：Sonnet、GPT-Terra/Luna，可按实际可用模型调整），在满足任务质量的前提下，优先降低模型调用成本、缩短响应耗时。
- 仅以下情况允许单代理执行，且必须在回复中说明原因：
  - 任务涉及单一文件或强顺序依赖，无法拆分
  - 用户明确要求单代理
  - 当前工具环境不支持子代理
- 子代理任务必须拆分清楚文件责任边界，避免多个代理同时修改同一文件。
- 整合时由主代理统一检查 diff、测试和构建结果。

### 临时文件

- 开发、验证或自动化过程中产生的临时文件统一放到 `.temp/` 目录。
- 开发完成后清理 `.temp/` 中本次任务产生的文件，不要提交临时文件。

## 7. Git 约定

- 开始修改前确认仓库处于干净状态（如 `git status`），避免在未提交的改动上叠加新变更。
- 开发任务完成并通过必要验证后，确认待提交内容无误再创建提交；若因用户要求、验证未通过或环境限制暂时不能提交，必须在最终回复中说明原因和当前未提交状态。
- 保持提交聚焦：功能代码、文档、配置、测试修复尽量分开提交。
- 提交说明应概括变更意图，而非罗列文件改动。
- 不要提交 `node_modules/`、`dist/`、`.vite/`、`.temp/` 等构建产物、临时目录和本地日志；确保上述目录已在 `.gitignore` 中配置。
- 禁止回滚用户未要求回滚的改动。
